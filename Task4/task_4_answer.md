# Архитектура продажи ОСАГО онлайн

## Контекст

InsureTech запускает онлайн-оформление ОСАГО. Пользователь заполняет заявку с данными автомобиля, после чего сервис должен запросить предложения у всех доступных страховых компаний.

Бизнес-требование: предложение от каждой страховой компании должно появляться на экране сразу после получения ответа от этой компании. Максимальное время ожидания ответа от страховой компании — 60 секунд.

Пиковая нагрузка может достигать 2500 одновременных пользователей, создающих заявку на ОСАГО.

Страховые компании предоставляют однотипные REST API:

- создать заявку на ОСАГО;
- получить предложение по заявке.

Команда уже приняла два базовых решения:

- сохранить подход с отдельным сервисом интеграции со страховыми компаниями;
- выделить новый сервис `osago-aggregator` для заявок и предложений ОСАГО.

## Предусловия

1. `core-app` остаётся владельцем пользовательского сценария ОСАГО: принимает заявку, валидирует данные, хранит состояние пользовательской заявки, показывает результаты и продолжает оформление выбранного предложения.
2. `osago-aggregator` отвечает только за техническую интеграцию со страховыми компаниями по ОСАГО: создание внешних заявок, polling предложений и публикацию результатов.
3. Сервисы запущены в Kubernetes в нескольких экземплярах, поэтому решение не должно зависеть от памяти конкретного pod-а.
4. В целевой архитектуре уже используется Kafka для событийной интеграции между сервисами.
5. Для надёжной публикации событий применяется `Transactional Outbox`.
6. Доставка событий рассматривается как `at-least-once`, поэтому потребители должны быть идемпотентными.
7. Внешние API страховых компаний могут отвечать медленно, быть временно недоступными или иметь собственные ограничения по нагрузке.

## Решение

Выбираем асинхронную архитектуру поиска предложений ОСАГО.

Пользовательский сценарий разделяется на команду запуска поиска и поток поступающих результатов:

1. Веб-приложение отправляет заявку в `core-app`.
2. `core-app` создаёт внутренний `quoteRequestId`, сохраняет заявку в `core-db` и вызывает `osago-aggregator`.
3. `osago-aggregator` сохраняет состояние поиска в собственной БД, создаёт заявки во всех страховых компаниях и запускает polling предложений.
4. Когда от страховой компании приходит предложение, `osago-aggregator` сохраняет результат и публикует событие в Kafka.
5. `core-app` получает событие, сохраняет предложение в `core-db` и отправляет его веб-приложению через SSE.
6. Через 60 секунд поиск завершается. Страховые компании без ответа получают статус `TIMEOUT`.

Ключевой принцип: активное состояние поиска хранится в БД, а не в памяти приложения. Это позволяет переживать рестарты, масштабировать сервисы горизонтально и восстанавливать поток результатов после переподключения пользователя.

## Хранилище `osago-aggregator`

`osago-aggregator` должен иметь собственное хранилище данных.

Без БД сервис был бы stateful, т.к. хранил бы состояние долгого 60-секундного процесса в памяти.
Это рискованно: при рестарте pod-а активные поиски потеряются, а при нескольких репликах появится риск двойного polling одной и той же заявки.

В `osago-aggregator-db` нужны основные сущности:

- `osago_quote_request` — общий поиск предложений: `quote_request_id`, ссылка на заявку в `core-app`, статус, время создания, `deadline_at`.
- `osago_company_request` — состояние запроса в конкретную страховую компанию: `company_id`, `external_request_id`, статус, номер попытки, `next_poll_at`, `locked_until`, последняя ошибка.
- `osago_offer` — полученное предложение: страховая компания, цена, условия, срок действия, внешний идентификатор.
- `outbox` — события, которые должны быть опубликованы в Kafka.

Для работы нескольких реплик polling-задачи должны забираться через lease/lock, например через `SELECT ... FOR UPDATE SKIP LOCKED` или аналогичный механизм. Уникальный ключ `quote_request_id + company_id` защищает от дублей по одной страховой компании.

## API `osago-aggregator` для `core-app`

`osago-aggregator` предоставляет `core-app` короткий синхронный API для команд. Этот API не должен ждать ответа страховых компаний.

Основной endpoint:

```http
POST /internal/v1/osago/quote-requests
Idempotency-Key: <core-generated-key>
```

Назначение: запустить поиск предложений ОСАГО.

Пример ответа:

```json
{
  "quoteRequestId": "qr-123",
  "status": "ACCEPTED",
  "deadlineAt": "2026-06-28T14:01:00Z"
}
```

Дополнительные endpoints:

- `GET /internal/v1/osago/quote-requests/{quoteRequestId}` — получить snapshot состояния поиска для диагностики или восстановления.
- `POST /internal/v1/osago/quote-requests/{quoteRequestId}/cancel` — отменить поиск, если пользователь покинул сценарий.

Результаты поиска передаются не REST callback-ом, а событиями через Kafka:

- `OsagoQuoteStarted`
- `OsagoOfferReceived`
- `OsagoCompanyQuoteFailed`
- `OsagoCompanyQuoteTimedOut`
- `OsagoQuoteCompleted`

Ключ Kafka-сообщения — `quoteRequestId`, чтобы события одного поиска обрабатывались в правильном порядке. В каждом событии должен быть `eventId` для идемпотентной обработки.

## Интеграция `core-app` и `osago-aggregator`

Выбрана комбинированная интеграция:

- `core-app -> osago-aggregator`: REST для запуска и отмены поиска;
- `osago-aggregator -> Kafka -> core-app`: события для поступающих предложений и финального статуса.

REST подходит для короткой команды "начать поиск". Kafka подходит для результатов, потому что предложения приходят частями и в разное время.

Такой подход не держит длинный HTTP-запрос между `core-app` и `osago-aggregator` в течение 60 секунд и не заставляет пользователя ждать самый медленный ответ.

## API `core-app` для веб-приложения

Для веб-приложения `core-app` предоставляет API из двух частей: командный REST API и поток событий.

Создание поиска:

```http
POST /api/v1/osago/quote-requests
```

Ответ:

```json
{
  "quoteRequestId": "qr-123",
  "status": "ACCEPTED",
  "deadlineAt": "2026-06-28T14:01:00Z",
  "eventsUrl": "/api/v1/osago/quote-requests/qr-123/events"
}
```

Получение текущего состояния:

```http
GET /api/v1/osago/quote-requests/{quoteRequestId}
```

Этот endpoint возвращает snapshot: какие страховые компании уже ответили, какие ещё ожидаются, какие завершились ошибкой или timeout.

Поток результатов:

```http
GET /api/v1/osago/quote-requests/{quoteRequestId}/events
Accept: text/event-stream
```

Для потока результатов выбран SSE.

SSE подходит лучше, чем REST polling, потому что при 2500 одновременных пользователей polling каждую секунду создавал бы 2500 дополнительных запросов в секунду только на проверку статуса. WebSocket тоже возможен, но здесь он избыточен: основной поток данных идёт от сервера к браузеру, а SSE проще поддерживает переподключение через `Last-Event-ID`.

События SSE:

- `offer-received`;
- `company-failed`;
- `company-timeout`;
- `quote-completed`.

SSE не является единственным источником истины. `core-app` сохраняет все полученные предложения и статусы в `core-db`, поэтому браузер может переподключиться к другой реплике и восстановить пропущенные события.

## Паттерны отказоустойчивости

### Web -> `core-app`

Применяются:

- `Rate Limiting` — ограничить частоту создания заявок по пользователю, сессии или IP.
- `Timeout` — ограничить время командных REST-запросов.
- `Retry` — использовать для SSE reconnect с `Last-Event-ID`; повтор `POST` допустим только с idempotency key.

### Партнёры -> `core-app`

Применяются:

- `Rate Limiting` — ограничить нагрузку по партнёру, например договорные 20 RPS.
- `Timeout` — ограничить время обработки входящих запросов.

### `core-app` -> `osago-aggregator`

Применяются:

- `Timeout` — команда запуска поиска не должна зависать.
- `Retry` — короткие повторы только для идемпотентного запроса с `Idempotency-Key`.
- `Circuit Breaker` — при деградации `osago-aggregator` `core-app` должен быстро вернуть ошибку или временную недоступность сценария, а не копить зависшие запросы.

### `osago-aggregator` -> страховые компании

Применяются:

- `Rate Limiting` — отдельный лимит на каждую страховую компанию.
- `Timeout` — отдельный timeout на создание заявки и каждый poll-запрос.
- `Retry` — только для сетевых ошибок и 5xx, с backoff.
- `Circuit Breaker` — отдельный breaker на каждую страховую компанию.

Важное правило: отказ одной страховой компании не должен ломать весь поиск. Если одна компания недоступна, остальные продолжают отдавать предложения.

### Kafka consumers

Применяются:

- `Retry` с backoff для временных ошибок обработки.
- `Dead Letter Queue` для сообщений, которые не удалось обработать после нескольких попыток.
- идемпотентная обработка по `eventId`.

## Работа в нескольких репликах

Решение не зависит от конкретной реплики сервиса.

Для `osago-aggregator`:

- API-реплики stateless;
- состояние поиска и polling-задачи хранятся в `osago-aggregator-db`;
- workers берут задачи через lock/lease;
- дубли предотвращаются уникальными ключами и идемпотентностью;
- события публикуются через `Transactional Outbox`.

Для `core-app`:

- события из Kafka сохраняются в `core-db`;
- SSE-поток строится поверх сохранённых событий и snapshot-а;
- пользователь может переподключиться к другой реплике;
- обработчики Kafka идемпотентны по `eventId`.

Если хранить активные предложения только в памяти pod-а, понадобятся sticky sessions, а при падении pod-а пользователь потеряет результаты. Поэтому источник истины должен быть в БД.
