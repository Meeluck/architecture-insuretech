# Описание решения задания 1

## 1. **Определите стратегию масштабирования и отказоустойчивости.** 

Рассмотрите вертикальное и горизонтальное масштабирование для вашей системы. Оцените, какая стратегия будет эффективнее.
Требуется ли использование дополнительных зон безопасности?

Для данного кейса вертикальное масштабирование может быть временной мерой для увеличения производительности отдельных узлов, но оно не решает ключевые требования: отказоустойчивость, RTO 45 минут, RPO 15 минут и доступность 99,9%.

Поэтому основная стратегия — горизонтальное масштабирование.

Приложения следует разворачивать в нескольких экземплярах и распределять их по независимым зонам доступности.

Для stateless-сервисов предпочтительна схема active-active: все зоны одновременно принимают трафик, а балансировщик исключает неисправные экземпляры по health check.

Так как бизнес требует одинакового времени загрузки страниц для пользователей из разных регионов РФ, необходимо добавить географическое распределение: использовать CDN для статического контента и GeoDNS для направления пользователей в ближайший доступный регион.

Оптимальная стратегия: active-active для приложений внутри региона и между регионами, с автоматическим failover при отказе зоны или региона.

## 2. Проработка конфигурацию развёртывания приложения в Kubernetes

Для каждой площадки будет развёрнут независимый Kubernetes-кластер.
Такой подход луче, чем один растянутый кластер, потому что отказ одной площадки не влияет на control plane, etcd и служебные компоненты Kubernetes в другой площадке.

Один растянутый кластер между регионами или удалёнными зонами усложняет эксплуатацию: он чувствителен к сетевым задержкам, потере связности между площадками и split-brain-сценариям. При проблемах с сетью кластер может некорректно определять состояние нод и подов, а восстановление становится сложнее.

В независимой схеме каждый кластер обслуживает свою долю трафика. Распределение пользователей между площадками выполняется не средствами Kubernetes, а внешним уровнем балансировки: Global Load Balancer / DNS / GeoDNS / CDN. Внутри каждой площадки Kubernetes Service / Ingress распределяет трафик между подами.

Для приложений используется active-active: сервисы запущены в нескольких репликах в каждом кластере. Если одна площадка выходит из строя, глобальный балансировщик исключает её по health check и направляет трафик на оставшиеся площадки.

Чтобы пережить отказ площадки без деградации, кластеры должны иметь запас ресурсов или настроенный autoscaling. Иначе сервис останется доступным, но время ответа может ухудшиться из-за роста нагрузки на оставшиеся площадки

## 3. Балансировка нагрузки

Балансировка нагрузки будет организована на нескольких уровнях.

Первый уровень — глобальная балансировка между регионами. Для этого используется GeoDNS или Global Load Balancer. Он направляет пользователя в ближайший доступный регион с учётом географического положения и результатов health check. Если регион недоступен, трафик переводится в другой регион.

Второй уровень — балансировка внутри региона между зонами доступности. Так как приложения работают по схеме active-active, трафик распределяется между несколькими зонами доступности. Для HTTP/REST-трафика используется региональный L7 Load Balancer, так как он позволяет выполнять маршрутизацию на уровне HTTP, TLS termination и health check на уровне приложения. Для TCP-трафика при необходимости может использоваться L4 Load Balancer.

Третий уровень — балансировка внутри Kubernetes-кластера. Входящий трафик обрабатывается через Gateway API, далее направляется в Kubernetes Service нужного приложения: core-app, client-info, ins-product-aggregator или ins-comp-settlement. Service распределяет запросы между pod’ами приложения. Неготовые pod’ы исключаются из балансировки через readiness probe, а неработающие перезапускаются по liveness probe.

## 4. Failover-стратегия

Наиболее подходящая failover-стратегия для приложения — active-active. 

Все регионы и зоны доступности одновременно обслуживают пользовательский и партнёрский трафик. Пользователь направляется в ближайший доступный регион через GeoDNS / Global Load Balancer. Внутри региона трафик распределяется между доступными зонами, а внутри Kubernetes — между pod’ами приложения через Gateway API и Service.
Если выходит из строя отдельный pod, Kubernetes исключает его из трафика по readiness probe и пересоздаёт через Deployment.

Если выходит из строя зона доступности, региональный балансировщик перестаёт направлять туда трафик по health check и перераспределяет нагрузку на оставшиеся зоны региона.

Если выходит из строя весь регион, Global Load Balancer / GeoDNS исключает регион из маршрутизации и переводит пользователей в другой доступный регион.
Такая стратегия минимизирует время переключения, так как резервные площадки уже работают и принимают трафик. Это лучше соответствует RTO 45 минут и доступности 99,9%, чем active-passive, где резервная площадка может потребовать прогрева, ручного переключения или дополнительной проверки перед приёмом трафика.

## 4 Конфигурацию базы данных

Шардирование БД не применяем. Объём данных составляет 50 GB, что не требует горизонтального разделения данных. Основные требования связаны с отказоустойчивостью, RTO 45 минут и RPO 15 минут. Поэтому вместо шардирования используем PostgreSQL HA-кластер с репликацией, автоматическим failover и резервным копированием

Для PostgreSQL разворачивается отказоустойчивый кластер. В основном регионе используется один primary-инстанс для записи и несколько replica-инстансов для чтения. Инстансы БД размещаются в разных зонах доступности. При отказе primary происходит автоматическое переключение на одну из реплик.

Для защиты от отказа региона дополнительно создаётся асинхронная реплика в другом регионе. Она используется как disaster recovery-площадка. В случае недоступности основного региона выполняется promote реплики до primary, после чего приложение переключается на новый endpoint БД.

Для обеспечения RPO 15 минут используется потоковая репликация PostgreSQL и архивирование WAL. Резервное копирование выполняется регулярно: full backup по расписанию и continuous WAL archiving для восстановления на точку во времени. Это позволяет восстановить данные с потерей не более 15 минут.

Для обеспечения RTO 45 минут failover должен быть автоматизирован. Для PostgreSQL можно использовать Patroni + etcd/Consul.
