# Задание 3. Переход на Event-Driven архитектуру

## Проблемы и риски текущей архитектуры

### 1. Синхронная цепочка зависит от внешних страховых компаний

Сейчас `core-app` и `ins-comp-settlement` получают продукты и тарифы через REST API сервиса `ins-product-aggregator`. В момент запроса агрегатор синхронно обращается во все страховые компании, собирает ответы и только после этого возвращает результат.

При подключении ещё пяти страховых компаний увеличит:

- общее время ответа, потому что операция начинает зависеть от самой медленной страховой компании
- вероятность таймаутов и ошибок, потому что сбой хотя бы одной внешней системы влияет на весь запрос
- риск каскадной деградации `core-app`, если пользовательские запросы начинают ждать медленные внешние API.

### 2. Локальные копии данных обновляются несогласованно

`core-app` обновляет данные о продуктах и тарифах раз в 15 минут, а `ins-comp-settlement` получает их раз в сутки. Из-за этого разные сервисы могут работать с разными версиями одних и тех же данных.

Сама идея локальных копий не является ошибкой. Проблема текущей архитектуры в том, что сейчас:

- нет явного владельца актуальной версии продукта и тарифа
- нет события, которое сообщает другим сервисам об изменении продукта или тарифа
- нет гарантированной доставки изменений
- нет версионирования тарифов, которое позволило бы понять, по каким условиям была оформлена конкретная страховка

Это критично для `ins-comp-settlement`: взаиморасчёты должны выполняться по тем условиям, которые действовали в момент оформления страховки, а не по случайно актуальной версии тарифа на момент ночного расчёта.

### 3. Ежедневный REST-запрос `ins-comp-settlement` в `core-app` создаёт сильную связность

`ins-comp-settlement` раз в сутки запрашивает в `core-app` все оформленные за день страховки. У этого подхода есть несколько рисков:

- если `core-app` недоступен ночью, расчёт сдвигается или не выполняется
- большой batch-запрос может создавать пиковую нагрузку на `core-app` и его БД
- при ошибке во время передачи нужно отдельно решать проблему повторного запуска и защиты от дублей
- `ins-comp-settlement` зависит от API `core-app`, хотя для расчётов ему нужна собственная проекция оформленных страховок.

При росте количества оформлений ежедневный пакетный обмен станет всё более тяжёлым и хрупким

## Целевое решение

### 1. Сделать `ins-product-aggregator` владельцем проекции продуктов и тарифов

В `ins-product-aggregator` нужно добавить собственную БД или отдельную схему БД для хранения актуальной проекции продуктов и тарифов страховых компаний.

Агрегатор должен не обслуживать каждый запрос через синхронный fan-out во все страховые компании, а самостоятельно и периодически обновлять данные:

1. По расписанию или через фоновые workers запрашивать продукты и тарифы у страховых компаний.
2. Сохранять полученные данные в свою БД.
3. Определять изменения относительно предыдущей версии.
4. Публиковать события об изменениях в брокер сообщений.

Примеры событий:

- `InsuranceProductCreated`
- `InsuranceProductUpdated`
- `InsuranceProductDisabled`
- `InsuranceTariffUpdated`

Так `core-app` и `ins-comp-settlement` смогут хранить локальные read-модели, но обновлять их не по несогласованному polling, а через поток событий.

### 2. Перевести получение продуктов и тарифов на Event Streaming

Взаимодействия:

- `core-app -> ins-product-aggregator` для регулярного получения продуктов и тарифов
- `ins-comp-settlement -> ins-product-aggregator` для регулярного получения продуктов и тарифов

нужно заменить на подписку `core-app` и `ins-comp-settlement` на события из брокера.

После этого:

- `core-app` использует локальную read-модель продуктов и тарифов для пользовательских сценариев
- `ins-comp-settlement` использует свою локальную read-модель для взаиморасчётов
- недоступность одной из страховых компаний не блокирует пользовательский запрос напрямую
- временная проблема с внешним API влияет на свежесть данных, но не ломает всю синхронную цепочку.

REST API `ins-product-aggregator` можно оставить для административных операций, ручной сверки или получения снапшота, но не как основной механизм регулярной синхронизации.

### 3. Перевести передачу оформленных страховок из `core-app` в `ins-comp-settlement` на события

Ежедневный REST-запрос `ins-comp-settlement -> core-app` нужно заменить на поток событий из `core-app`.

`core-app` должен публиковать события жизненного цикла страховки:

- `PolicyCreated`
- `PolicyIssued`
- `PolicyPaid`
- `PolicyCancelled`

`ins-comp-settlement` подписывается на эти события и постепенно формирует у себя проекцию оформленных страховок, нужную для расчётов со страховыми компаниями.

Так `ins-comp-settlement` перестаёт зависеть от ночного batch-запроса в `core-app` и может выполнять расчёты на основе собственной БД.

### 4. Использовать Transactional Outbox

`Transactional Outbox` нужен минимум в двух местах.

Первое место — `ins-product-aggregator`. При обновлении продукта или тарифа агрегатор должен в одной транзакции:

1. Сохранить новую версию продукта или тарифа в свою БД.
2. Записать событие в таблицу `outbox`.

После этого отдельный publisher читает записи из `outbox`, публикует их в брокер и помечает как отправленные.

Второе место — `core-app`. При оформлении, оплате или отмене страховки `core-app` должен в одной транзакции:

1. Сохранить изменение статуса страховки в `core-db`.
2. Записать доменное событие в таблицу `outbox`.

Это защищает систему от ситуации, когда данные в БД уже изменились, а событие для других сервисов не было опубликовано.

### 5. Обеспечить идемпотентность

Потребители событий должны быть готовы к повторной доставке сообщений. Поэтому `core-app` и `ins-comp-settlement` должны обрабатывать события идемпотентно

## Итоговая целевая схема взаимодействий

В целевой архитектуре нужно добавить брокер сообщений, например Kafka или RabbitMQ, и изменить взаимодействия следующим образом:

1. `ins-product-aggregator` периодически получает данные от страховых компаний, сохраняет их в свою БД и через `Transactional Outbox` публикует события о продуктах и тарифах.
2. `core-app` подписывается на события продуктов и тарифов, обновляет свою локальную read-модель и использует её для пользовательских и партнёрских запросов.
3. `ins-comp-settlement` подписывается на события продуктов и тарифов, обновляет свою локальную read-модель и использует её для расчётов.
4. `core-app` при изменении жизненного цикла страховки публикует события через свой `Transactional Outbox`.
5. `ins-comp-settlement` подписывается на события оформленных страховок и формирует собственную проекцию для взаиморасчётов.

Такое решение снижает связность между сервисами, убирает зависимость пользовательских запросов от текущего состояния API страховых компаний, уменьшает ночные batch-нагрузки и делает обмен данными между сервисами более надёжным при росте числа пользователей и страховых партнёров.
